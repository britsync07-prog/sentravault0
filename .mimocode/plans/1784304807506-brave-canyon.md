# Sleep Mode & Large File Upload Analysis — AHS Vault Desktop App

## Summary of Findings

Your application is a **Tauri 2 desktop app** (Rust backend + React frontend). Here's exactly what happens with sleep mode, auto-lock, and large file uploads:

---

## 1. OS Sleep / Hibernate — YOUR APP DOES **NOT** PREVENT IT

**There is NO code anywhere in the codebase that prevents the PC from going to sleep.**

- No `powerSaveBlocker` (that's Electron — Tauri doesn't have an equivalent)
- No `wake_lock` API usage
- No `SetThreadExecutionState` (Windows API to prevent sleep)
- No `caffeinate` command (macOS equivalent)
- No Tauri plugin for power management
- Not in `Cargo.toml` dependencies, not in any Rust source, not in any JS/TS file

**Result**: If a user uploads a huge file and walks away, their PC **WILL go to sleep** whenever the OS decides (based on Windows power settings). The upload will be **interrupted**.

---

## 2. Auto-Lock (Application-Level Lock, NOT OS Sleep)

Your app has its own auto-lock system (separate from OS sleep):

### How it works (`lib.rs:572-637`):
- A background thread (`start_inactivity_watcher`) runs every 1 second
- It checks `LAST_ACTIVITY` timestamp against `AUTO_LOCK_TIMEOUT`
- Default timeout: **300 seconds (5 minutes)**
- **Options**: 1 min, 5 min, 15 min, 1 hour, **Never** (9999999 seconds ≈ 115 days)
- If "Never" is selected, auto-lock is effectively disabled

### Activity detection (`App.tsx:232-253`):
The frontend listens for: `mousedown`, `mousemove`, `keypress`, `scroll`, `touchstart`
Each event calls `invoke("reset_idle_timer")` which updates `LAST_ACTIVITY` in Rust.

### Critical: Auto-lock is SKIPPED during file transfers (`lib.rs:600-603`):
```rust
// If any file transfer is in progress, skip auto-lock
if ACTIVE_TRANSFERS.load(Ordering::SeqCst) > 0 {
    continue;
}
```

### TransferGuard RAII guard (`lib.rs:535-548`):
- Increments `ACTIVE_TRANSFERS` on creation
- Decrements on drop
- Used in: `upload_to_vault`, `download_from_vault`, WebDAV PUT handler, FUSE writes, cloud sync uploads

**Result**: When auto-lock is set to "Never" + file transfer is in progress → the app **will NOT auto-lock**. But the **OS can still sleep**.

---

## 3. "Wipe Keys on Sleep" Setting (`Dashboard.tsx:291-295`)

There's a toggle labeled **"Wipe Keys on Sleep"** with description:
> "Instantly erases all encryption keys from active state when the system enters sleep or hibernation."

**HOWEVER: This is only a UI toggle stored in localStorage.** It is:
- Saved to `localStorage` as `settings.wipeKeys`
- **NOT connected to any actual OS sleep/hibernate event listener**
- **NOT implemented in the Rust backend**
- There is no code that hooks into OS sleep events to wipe keys

This setting is **cosmetic only** — it doesn't actually do anything.

---

## 4. What Happens: User Uploads Huge File → Walks Away → PC Sleeps

Here's the complete chain:

1. **User starts upload** → `upload_to_vault` creates `TransferGuard` → `ACTIVE_TRANSFERS = 1`
2. **User walks away** → No more mouse/keyboard events → `LAST_ACTIVITY` stops updating
3. **PC goes to sleep** (OS power management, your app can't prevent this):
   - The `reqwest` HTTP upload in `stream_upload_blob` **will be interrupted** (TCP connection drops)
   - The FUSE filesystem on Linux **may corrupt pending writes**
   - On Windows, the network drive `M:` **will disconnect**
   - All encryption keys in memory **remain in RAM** (despite the "Wipe Keys on Sleep" toggle being cosmetic)
4. **PC wakes up**:
   - The WebSocket connection to the backend **drops** and enters reconnect loop (`network.rs:112-124`)
   - Auto-lock watcher resumes checking
   - Upload has failed silently (no retry logic in `stream_upload_blob`)
   - The `TransferGuard` was dropped when the async task died → `ACTIVE_TRANSFERS = 0`

---

## 5. Key Issues / Gaps

| Issue | Severity | Details |
|-------|----------|---------|
| **No OS sleep prevention** | HIGH | Large uploads will be killed when PC sleeps |
| **"Wipe Keys on Sleep" is cosmetic** | HIGH | False sense of security — keys stay in memory |
| **No upload retry on sleep/wake** | MEDIUM | Failed uploads are silently lost |
| **No chunked upload** | MEDIUM | `stream_upload_blob` sends entire file as one HTTP body — no resumability |
| **Upload uses blocking `reqwest`** | LOW | Blocks the thread during upload (but wrapped in async Tauri command) |

---

## 6. What Could Be Done (If You Want to Fix)

### Option A: Prevent Sleep During Transfers
- Add a Tauri plugin or raw Windows API call (`SetThreadExecutionState` with `ES_CONTINUOUS | ES_SYSTEM_REQUIRED`) when `ACTIVE_TRANSFERS > 0`
- Release when transfers complete

### Option B: Actually Implement "Wipe Keys on Sleep"
- Hook into OS sleep events (Windows: `RegisterPowerSettingNotification`, Tauri doesn't have this built-in)
- On sleep signal → call `crypto::clear_master_key()` to wipe keys from memory

### Option C: Add Chunked/Resumable Uploads
- Split large files into chunks before upload
- Store upload progress so it can resume after sleep/wake

### Option D: Do Nothing (Current State)
- Accept that large uploads may fail if PC sleeps
- Users should ensure their PC doesn't sleep during uploads (Windows power settings)
- The "auto-lock never" setting works correctly for app-level locking
